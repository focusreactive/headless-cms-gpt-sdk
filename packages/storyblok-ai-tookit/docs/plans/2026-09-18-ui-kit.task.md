# Thin UI kit — the pieces screen 1 is assembled from

Branch: feat/batch-and-markers · base 69579f9 · Risk: LOW
Upstream: [2026-09-17-brand-voice.md](./2026-09-17-brand-voice.md) and the design artifact.

## Scope

In: three wrappers in `src/ui/` — `Select`, `IconButton`, `Alert` — and a barrel.

Out: everything else. No data layer, no hooks, no context, no vitest, no
`@mui/icons-material`, no screens. Those are later tasks; this one prepares parts to
assemble from.

## What the kit is for

Not portability — the plugin lives inside `@storyblok/mui`, Storyblok's own theme, and
leaving MUI would mean no longer looking like Storyblok. The kit exists to hold the
density decisions in one place, so the next component does not re-decide them.

## Decisions

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Thin or insulating | **Thin** — a wrapper extends the MUI component's own props, so every native and MUI prop passes through untouched | Insulating (re-declaring a narrow prop set): every pass-through would be added by hand, and the insulation buys nothing when the theme is MUI's anyway |
| Our own props | Prefixed `$`, destructured out and never spread, so they cannot reach the DOM | Plain names: they collide with MUI's own and leak into the DOM |
| Who wins on conflict | Density props are **removed from the type** (`Omit`), so a caller cannot pass them at all; everything else the caller wins | Spread order alone: `size` after `{...rest}` silently ignores what the caller wrote, which reads as a bug at the call site |
| `Select`, not `Field` | A select is only a select | `Field`: MUI's own field concept is a polymorphic composite with variants and a select mode — the name invites the wrapper to grow into it |
| Tooltip | Folded into `IconButton` as `$label`, used for both the tooltip and `aria-label` | A standalone `Tooltip` wrapper: it carries no decision, and the real one — that an icon button always has a label, needed twice — belongs where the icon button is |

**New surface:** three components. Callers: screen 1 uses all three, screens 2 and 3 use
`IconButton` and `Select` again. `Tooltip` is deliberately not among them.

**Written contract:** none. These are pass-throughs; the types state everything.

# Batch two — `Button`, a tone on `IconButton`, and the confirm hook

Same branch, same conventions. Risk: LOW.

## Scope

`Button` in `src/ui/`, a `$tone` on the existing `IconButton`, and
`useTwoStepConfirm` in `src/shared/`. No consumers yet, as before.

## Decisions

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Where the two-step confirm behaviour lives | A standalone hook, composed with the kit at the call site | Inside the kit as a `ConfirmIconButton`: the kit is presentational by decision, and a component carrying arm/disarm, a timer and document listeners is not |
| What the hook knows | Nothing about any entity: `perform` takes no arguments, nothing is returned but state and handlers, no strings at all | Passing an id or a label: the caller closes over the id and writes its own "Delete Legal — tap again to confirm"; a hook that knows either can only serve one caller |
| How click-away is detected | The hook returns a `ref` the caller attaches | Leaving click-away and Escape to the caller: every consumer would then repeat the same three cancel paths, which is what the hook exists to prevent |
| Icon in a button | MUI's own `startIcon` | A `$icon` of ours: the native prop already does it, and a second name for one thing is how two ways of doing it start |
| Export shape | Flat, no namespace | A namespace: those are for a feature's own logic group; this hook belongs to no feature |

**New surface:** `Button` (callers: two buttons on screen 1, one on screen 2, three on
screen 3), `useTwoStepConfirm` (one caller today — the delete control on screen 2 — and
it exists as a hook rather than a component because the kit may not hold behaviour).

**Written contract:** none for the components. The hook owes callers one thing a
signature cannot state, recorded below rather than in a contract type, because it is a
single rule rather than a surface: **Escape is intercepted only while pending.** In the
resting state the handler does not fire at all and the key travels on untouched.

## Acceptance criteria

| # | Criterion | How it is checked | Pre-flight |
|---|---|---|---|
| 1 | `Button` rejects `size`, like its neighbours | a throwaway file assigning it, then `npx tsc --noEmit` | component absent — fails now |
| 2 | `IconButton` without `$tone` renders exactly as before | read the diff: the default branch changes nothing | fails now |
| 3 | `useTwoStepConfirm` returns no strings and takes no entity | read its signature and return type | fails now |
| 4 | Escape disarms while pending, and is not listened for at rest | read the effect: the listener is registered inside the `pending` branch, so at rest none exists | fails now |
| 5 | No new type errors | `npx tsc --noEmit` | **exit 0 — passes now, must stay** |

### Escape disarms; it does not take the key

Review found the first version overclaimed: `preventDefault` + `stopPropagation` on a
`document` listener in the bubble phase intercepts nothing that competes for Escape —
React's root container and MUI's own roots are descendants of `document` and answer
first. The guard was weightless against them, and *not* weightless against the browser's
own defaults, which it suppressed for as long as the button stayed armed.

**Chosen:** drop both calls. Escape disarms and travels on.

**Rejected:** register in the capture phase, which would make the interception real.
It buys nothing here — confirmation is inline by decision, so no dialog is ever open
while a button is armed — and it is exactly the Escape-stealing the owner named as
their one worry about this control.

### `timeoutMs` outside the finite positive range means "no decay"

`setTimeout` truncates its delay to an integer, so `Infinity` — the obvious way to ask
for no decay — arrived as `0` and disarmed in the next task, making confirmation
impossible with nothing logged. The timer is now only set for a finite positive value.

## Human choices

- **The hook ships unverified, deliberately.** Testing a React hook needs jsdom and a
  testing library, neither of which is in this package, and the user chose to keep the
  test runner for the data-layer task. This is recorded as debt, not as an oversight:
  the hook is the first thing in the kit that carries logic, and its three cancel paths —
  timeout, click-away, Escape-only-while-pending — are exactly the kind that break
  quietly.

# Batch four — the form fields, `Disclosure`, and two corrections

## Scope

The last batch of the kit: the four controls the preset form is built from, plus three
corrections to components already shipped. Nothing outside `src/ui/`, `src/shared/` and
this file. No new dependency: `@mui/icons-material` is **not** installed and is not being
added, so the one icon needed (the disclosure chevron) is drawn inline.

## Decisions

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Where `TagsInput`'s rules live | **Nowhere in the kit.** The component is fully controlled — `value: string[]`, `onChange(next)` — and the cap of 20, the duplicate rejection and the wording of both live at the call site | A `useTagList` hook in `shared/`: it has exactly one caller today, which the ≥2-callers rule forbids, and it would have to carry the cap and the rejection message — the entity knowledge the standing decision keeps out of shared hooks |
| Committing a typed word | **The component's job**, via Autocomplete's own `autoSelect`: Enter commits, and so does leaving the field | Leaving it to the caller: it is Autocomplete's built-in behaviour, and re-implementing it with `onBlur` at every call site is how two ways of doing one thing start |
| `Input` and `Textarea` as two files | Two, per the owner's decision. They stay genuinely distinct: `Textarea` sets `multiline` and owns `$minRows`; `Input` removes `multiline` from its type so it cannot become one | One `Input` with `$multiline`: rejected by the owner |
| How helper text reaches a field | `Input` and `Textarea` need nothing of ours — `TextField` already has native `helperText` and `error`. Only the two compound wrappers add `$helperText`, because neither `SelectProps` nor `AutocompleteProps` surfaces the inner field's | Adding `$helperText` to all four for symmetry: it would shadow a native prop on two of them, which is the `labelId` mistake again |
| `$loading` versus `startIcon` | `$loading` sets `disabled` and takes over `startIcon` **for its duration only**; without it `startIcon` passes through untouched | `Omit`-ing `startIcon`: the batch-two decision keeps it for callers, and an icon on a button that is never loading is legitimate |
| `Disclosure`'s open state | **Controlled** — `$open` and `onToggle`; the caller writes the `useState`. No `useDisclosure` file | A `useDisclosure` hook in `shared/` (asked for in the task, dropped at the gate): it is `useState` under another name with one caller. Also rejected: letting `Disclosure` own the state, which would make it the only stateful thing in a kit that is stateless by decision |
| `$error` on `TagsInput`, plain `error` everywhere else | The asymmetry stands. `TextField` has a native `error`, so `Input` and `Textarea` pass it through and `Select` routes it to `FormControl`, which propagates it by context. `AutocompleteProps` declares none, so `TagsInput` must own it and owns it under `$` | Naming ours `error` for symmetry: it would be the only unprefixed prop of ours in the kit, breaking the rule that tells a caller at a glance whose prop they are setting |
| The chevron | Inline SVG, rotated by CSS | `@mui/icons-material`: not installed, and a new runtime dependency in a hand-published package is a stop-and-ask, not a detail |

**New surface:** `Input`, `Textarea`, `TagsInput`, `Disclosure`. Callers: the preset form
(screen 3) uses all four; `Input` is used twice there (Name) and again by the list's
rename path. Nothing is added that the drawn screens do not use.

**Written contract:** none. Every one of these is a pass-through whose types state what
it owes, with one exception recorded under Human choices.

**Escalate to `/sp-architect`?** No. One module, no new seam, no dependency, no data.
